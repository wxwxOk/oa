<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| frontend store -> authenticated backend API | Store serializes untrusted formData and IDs; backend remains source of truth |
| UI status helpers -> rendered actions | Client-side visibility improves UX but must not be treated as authorization |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-01 | I/E | `fetchDetail`, `updateDraft`, `submit`, `cancel` | mitigate | Store never adds department/all-applicant filters; it calls own endpoints only and leaves ownership enforcement to backend. |
| T-17-02 | T | `submit` payload | mitigate | Store sends only `formData`; required validation remains backend-enforced and frontend form validation is added in Plan 17-04. |
| T-17-04 | T/E | `createDraft`, `submit` payload types | mitigate | DTOs intentionally exclude `schemaSnapshot`, `processSnapshot`, `applicationNo`, applicant, and department snapshot inputs. |
| T-17-06 | D | store action loading states | mitigate | Store exposes loading flags for save/submit/cancel so pages can disable duplicate clicks; backend still rejects invalid transitions. |
</threat_model>
