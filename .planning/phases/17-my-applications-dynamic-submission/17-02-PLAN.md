<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `/api/v1/approval/applications` | Untrusted authenticated request payloads and IDs enter internal approval APIs |
| `/api/v1` app group -> public `/api/public/f` group | Internal approval routes must stay JWT-protected and separate from public collection |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-01 | I/E | `GET /:id`, `PUT /:id/draft`, `POST /:id/submit`, `POST /:id/cancel` | mitigate | Use service helpers that enforce applicant ownership; route tests must prove route bodies cannot bypass service ownership checks. |
| T-17-02 | T | `POST /:id/submit` | mitigate | Body accepts only optional `formData`; handler delegates to `submitDraftApplication` required-field validation before workflow submit. |
| T-17-04 | T/E | `POST /drafts`, `POST /:id/submit` | mitigate | TypeBox bodies must not include `applicationNo`, `schemaSnapshot`, `processSnapshot`, applicant snapshot, or process fields. |
| T-17-05 | I/E | `backend/src/index.ts` registration | mitigate | Register `approvalApplicationModule` inside `.group('/api').group('/v1')` next to `approvalProcessModule`; never under `publicFillModule`. |
| T-17-06 | D/T | submit/cancel routes | mitigate | Route handlers do not implement state changes directly; duplicate submit/cancel attempts flow through service/state-machine rejection and frontend will disable duplicate clicks in later plans. |
</threat_model>
