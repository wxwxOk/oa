## Scope Boundary

Phase 18 UI includes:
- Approver navigation entry for `待我审批`.
- `待办` and `已处理` task views with task-scoped filters.
- Approval task detail driven by task ID, not applicant-owned application ID.
- Read-only snapshot rendering of application form content.
- Approve, reject, and internal remark flows for authorized approvers.
- Mobile task cards, mobile filter sheet, and sticky bottom approve/reject actions.

Phase 18 UI excludes:
- Applicant `我的申请` changes beyond internal remark visibility filtering.
- Department-wide queues, all-task views, delegation, transfer, batch approval, or admin proxy approval.
- Tags, marks, post-submit field editing, processing fields, archive search, export, statistics, notifications, attachments, and advanced workflow branches.
- List-row quick approve/reject actions.

Source: `18-CONTEXT.md` D-01 through D-30, `ROADMAP.md`, `REQUIREMENTS.md` APR-01 through APR-06.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, compact chip spacing, helper text separation |
| sm | 8px | Mobile card internal gaps, timeline comment spacing, button gaps |
| md | 16px | Default page spacing, card padding, filter gaps, dialog inner spacing |
| lg | 24px | Desktop section spacing, detail column gaps, sticky bar inner padding |
| xl | 32px | Major page section separation, desktop header-to-content spacing |
| 2xl | 48px | Empty/error/loading vertical padding |
| 3xl | 64px | Large empty-state breathing room only |

Exceptions:
- `44px` minimum touch target for mobile filter trigger, sheet actions, card actions, sticky approve/reject buttons, and remark trigger.
- `56px` minimum row height for tappable mobile filter rows and template/task list actions that include icon + label.
- `1px` borders for cards, tables, dialog dividers, timeline separators, and sticky action bar top border.
- Mobile sticky action region uses `16px` horizontal padding and `16px + env(safe-area-inset-bottom, 0px)` bottom padding.
- Detail pages reserve at least `96px` bottom content padding on mobile so sticky actions never cover long forms, signatures, or timeline items.

## Typography

Use exactly two weights: regular `400` and semibold `600`.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Caption / metadata | 12px | 400 | 1.5 |
| Body / form snapshot / timeline comment | 14px | 400 | 1.5 |
| Section / card title | 16px | 600 | 1.4 |
| Page / dialog heading | 20px | 600 | 1.2 |

Rules:
- Page titles and dialog titles use the existing `.text-h6` override at 20px, 600, 1.2.
- Mobile card primary text may use Quasar `text-subtitle1` but must render at 16px or below.
- Approver comments, internal remarks, node names, template names, and application numbers must wrap on 375px screens without horizontal overflow.
- Timeline metadata stays at 12px; comment bodies stay at 14px with `white-space: pre-wrap`.
- Sticky action buttons use default Quasar button typography; do not create oversized hero buttons.

## Layout And Component Contract

### Navigation

- Add `待我审批` under existing `审批管理` in `MainLayout.vue`.
- Route: `/approval/tasks`.
- Icon: material icon `fact_check`.
- Visibility permission: `approval:task:list`.
- Keep `我的申请` and `流程配置` unchanged; do not merge approver tasks into applicant lists.

### Approval Task List Page

Use the Phase 17 approval list pattern as the base, with a task-centered mode switch.

Desktop layout:
- Container: `q-page padding`.
- Header: left title `待我审批`, right filter reset/reload controls only; there is no create CTA in this phase.
- Under header, place a top-level mode switch for `待办` and `已处理`. Use `q-tabs` or `q-btn-toggle`, but active state must use the accent contract and remain visually distinct from secondary filters.
- Pending is the default tab on first entry.
- Filters render in a horizontal row below the mode switch.
- Desktop filters include:
  - Template filter: `q-select`, label `申请类型`, clearable.
  - Applicant filter: `q-input`, label `申请人`.
  - Department filter: `q-select`, label `部门`, clearable.
  - Status filter:
    - Pending tab: hidden or read-only fixed to `待处理`.
    - Handled tab: `全部 / 已通过 / 已驳回 / 已关闭` with `已关闭` optional and visually secondary.
  - Date range: two dense outlined date inputs; labels change by tab to `分配开始日期 / 分配结束日期` for pending and `处理开始日期 / 处理结束日期` for handled.
- Data view: `q-table flat bordered dense`, rows-per-page `[10, 20, 50]`, sorted newest first by assignment time on pending and handled time on handled.

Desktop table columns:

| Column | Label | Width | Content |
|--------|-------|-------|---------|
| applicationNo | 申请编号 | 140px | stable backend-generated application number |
| templateName | 申请类型 | auto | template snapshot name + `v{templateVersion}` caption |
| applicant | 申请人/部门 | 180px | applicant name on first line, department on second line |
| nodeName | 当前节点 | 140px | current node name or handled node name |
| taskStatus | 任务状态 | 96px | task status chip |
| applicationStatus | 申请状态 | 96px | application status badge/text |
| time | 分配时间 / 处理时间 | 160px | `YYYY-MM-DD HH:mm`, label changes by tab |
| actions | 操作 | 120px | pending: `处理审批`; handled: `查看详情` |

Mobile layout:
- Header contains title plus one round icon button for opening the filter sheet.
- Mode switch stays visible at top and spans full width.
- Task rows use `q-card flat bordered` in a vertical list.
- Card information order:
  1. Application type
  2. Task status chip
  3. Application number
  4. Applicant and department
  5. Current node
  6. Assignment or handled time
  7. Application status
- Entire card is tappable and routes to detail.
- Card action row contains a single text button: pending uses `处理审批`; handled uses `查看详情`.

### Mobile Filter Sheet

- Use a bottom `q-dialog position="bottom"` sheet consistent with Phase 17 and existing `FilterSheet.vue`.
- Top corners may keep the existing `16px` radius.
- Include a drag handle, title `筛选任务`, and stacked controls with 16px gaps.
- Buttons:
  - Secondary: `重置筛选`
  - Primary: `应用筛选`
- All interactive controls must be at least 44px tall.
- Closing the sheet without applying does not mutate the live list state.

### Empty, Error, And Loading States

- Pending empty state:
  - Icon `fact_check`
  - Heading `暂无待办审批`
  - Body `当前没有待你处理的审批任务，可切换到已处理查看历史记录。`
- Handled empty state:
  - Icon `history`
  - Heading `暂无已处理记录`
  - Body `你处理过的审批任务会显示在这里，便于回看审批结果和意见。`
- List error state uses centered copy with a single primary `重新加载` button.
- Initial loading:
  - Desktop: one filter skeleton row + table header + 5 body rows.
  - Mobile: 3 bordered task card skeletons matching final card density.

### Approval Task Detail

Use a full-page detail route rather than a drawer because the approver must review long historical form snapshots before acting.

- Route: `/approval/tasks/:id`.
- Desktop layout: `q-page padding`, max content width `1184px`, two columns.
- Left column order:
  1. `申请信息` summary card
  2. `表单内容` snapshot card
- Right column order:
  1. `当前任务` card
  2. `审批动态` timeline card
- Mobile layout: single column with this order:
  1. Header
  2. Current task card
  3. Application info card
  4. Form snapshot card
  5. Timeline card
  6. Sticky bottom approve/reject actions when task is pending and user has `approval:task:handle`

Header contract:
- Left back button with tooltip/aria-label `返回待我审批`.
- Title `审批详情`.
- Show task status chip first and application status chip second.
- Do not expose edit affordances for applicant form data.

Application info card fields:
- 申请编号
- 申请类型 `模板名 v版本`
- 申请人
- 部门
- 提交时间
- 完成时间
- 当前节点
- 审批流程说明 hint: `表单内容按提交时快照展示，当前模板变更不会影响本次审批。`

Current task card fields:
- 任务状态
- 申请状态
- 当前节点
- 分配时间
- 处理时间
- 当前审批人
- Pending detail shows a muted note: `请确认申请编号、申请类型和节点无误后再处理。`
- If the task is already handled, replace action copy with a read-only result summary.

Form snapshot contract:
- Must render from `schemaSnapshot + formData`.
- Use `GridFormRenderer mode="print"`.
- On mobile, dynamic table print rendering must keep the Phase 17 block layout fallback so long rows wrap vertically.
- Missing values show `—`, not blank.

Timeline contract:
- Reuse or extend `ApplicationTimeline`.
- Order is oldest to newest.
- Event titles:
  - `SUBMIT`: `提交申请`
  - `ASSIGN`: `进入 {nodeName}`
  - `APPROVE`: `审批通过`
  - `REJECT`: `审批驳回`
  - `CANCEL`: `申请已撤销`
  - `COMMENT`: `内部备注`
- Each item shows actor, node when present, comment when present, and timestamp.
- Comments and remarks must preserve line breaks and wrap on narrow screens.
- Approver detail may show internal remarks; applicant own-detail must not.

### Approve / Reject Interaction

- Approve and reject actions appear only in a pending task detail for the current assignee with `approval:task:handle`.
- There is no list-row quick action.
- Desktop actions live inside the `当前任务` card footer.
- Mobile actions live in a sticky bottom bar with two buttons:
  - Left: `驳回`, outline or tonal negative
  - Right: `通过`, solid primary
- Sticky bar must sit on a surface color, include a top border, and reserve safe-area padding.

Approve confirmation dialog:
- Title: `确认通过审批`
- Body includes:
  - `申请编号：{applicationNo}`
  - `申请类型：{templateName}`
  - `当前节点：{nodeName}`
  - helper copy `通过后任务将流转到下一节点或直接完成审批。`
- Textarea label: `审批意见（选填）`
- Max length: 200
- Confirm button: `确认通过`

Reject confirmation dialog:
- Title: `确认驳回审批`
- Body includes the same summary block.
- Warning copy: `驳回后申请将直接结束，并关闭全部未处理待办。`
- Textarea label: `驳回意见`
- Opinion is required.
- Max length: 200
- Confirm button: `确认驳回`
- Confirm button uses destructive color.

Action result rules:
- Success refreshes detail, pending list, and handled list counters/data.
- If approval moved to a next node, current task becomes handled and application status stays `审批中`.
- If approval completed the final node, application status becomes `已通过`.
- If rejection succeeded, application status becomes `已驳回` and pending actions disappear.

### Internal Remark

- Internal remark is a secondary action, never part of the sticky primary action bar.
- Entry point:
  - Desktop: text button `添加内部备注` in the `当前任务` card.
  - Mobile: full-width outline button above the timeline card or inside the current task card.
- Dialog title: `添加内部备注`
- Textarea label: `备注内容`
- Max length: 200
- Confirm button: `保存备注`
- Only users with `approval:task:handle` see this control.
- Pending-task approvers can always add remarks.
- Handled-task approvers may still add remarks in handled detail if the backend permits it.
- Saved remarks append to the timeline as `内部备注` and never alter the submitted form content.

## State Matrix

| State | Visual Contract |
|-------|-----------------|
| Initial list loading | Desktop shows filter skeleton + table skeleton. Mobile shows 3 bordered task card skeletons. |
| Pending list empty | `EmptyState` with `fact_check`, pending empty copy, and no misleading primary CTA. |
| Handled list empty | `EmptyState` with `history`, handled empty copy. |
| List error | Centered message `审批任务加载失败，请检查网络后重试。` + primary `重新加载`. |
| Pending list data | Default tab is `待办`; rows/cards show task status first, application status separately, and only a detail action. |
| Handled list data | `已处理` view separates handled records from current pending queue; handled time replaces assignment time. |
| Pending detail loading | Summary skeleton + current task skeleton + form snapshot skeleton + timeline skeleton. |
| Detail error | Bordered card with `审批详情加载失败，请检查网络后重试。` and `重新加载`. |
| Pending detail data | Sticky approve/reject actions visible on mobile; desktop actions live in current-task card; remark trigger visible. |
| Handled detail data | No approve/reject controls; task result summary remains visible; remark action may remain visible if authorized. |
| Approve dialog open | Summary block visible, optional comment field, primary focus on confirm/cancel. |
| Reject dialog open | Summary block visible, required textarea, destructive confirm button disabled until opinion is non-empty. |
| Remark dialog open | Single textarea dialog with 200-char counter and primary `保存备注`. |
| Action submitting | Confirm buttons show loading and block duplicate submissions; sticky buttons are disabled until request resolves. |
| Action success | Positive `Notify`, detail refresh, pending/handled datasets refresh, status chips update immediately after reload. |
| Stale or unauthorized task | Negative `Notify` uses backend `BizError` message or `该任务已被处理或已失效，请刷新列表。`; actions disappear after refresh when no longer valid. |

## Accessibility And Interaction Rules

- All icon-only buttons require `aria-label` or `q-tooltip`: back, filter trigger, close dialog, date picker, reload, detail navigation.
- Keyboard tab order follows visual order: mode switch, filters, list actions, detail actions, dialogs.
- Focus ring uses existing global `--oa-focus-ring`; do not remove Quasar focus outlines.
- Mobile touch targets are at least 44px high for all primary actions and filter controls.
- Entire mobile task cards use `cursor-pointer` and visual feedback on tap/hover without layout shift.
- Status is always shown with text plus color.
- Sticky bottom actions must not overlap scroll content; detail container must reserve bottom padding before the sticky bar.
- Timeline comments and internal remarks use `white-space: pre-wrap` and `overflow-wrap: anywhere`.
- Dynamic table print content on mobile must stay readable with Phase 17 block conversion; no horizontal page overflow at 375px.
- Dialog textareas show remaining length via the standard counter and keep labels visible.
- Loading states reserve layout space and avoid content jumping.
- Respect existing app motion levels: hover transitions 150-200ms, no oversized bounce or scale effects.
